Plugins

This page records the owner's intended use. The Core Plugin interface and SDK client are built. Simulations use scripted Plugins; no operational Plugin exists yet.

A Plugin is a small program that runs beside Core and offers actions. An operator runs an action with inputs, such as an area or a building. The Plugin uses its tools, often open-source services, to gather and return information.

Where Plugins sit

  • Plugins sit in the second ring of the walled city. Each one runs on its own, in its own container if it needs one once containers arrive, and connects out to Core with a key an admin gave it. It reaches Core only through its Plugin interface, never its storage. The Plugin interface is the Core API with a Plugin key, not a second protocol. Reading the shared picture, creating geo features, and storing Objects go through that interface.
  • The Core API carries Plugin calls. That is how the Command Interface uses a Plugin from outside the city. The Core API has the calls.
  • Operators call Plugins first. Assets will be able to call them later.
  • Plugins do not direct Assets or issue Tasks.
  • A feed that sends data all the time, such as an internet aircraft feed, is an Asset, not a Plugin.

Actions

Each Plugin describes its own actions, like a form: a name, a label, and the inputs each one takes. Inputs come from a fixed set of common pieces Atlas defines: an area, a position, a time, a place already on the map, a number, a short text, or a choice from a list the Plugin gives. An input may be optional. Core checks every call against the Plugin's form and every answer against Atlas's one answer shape, so adding or changing a Plugin never changes Protocol. Each action also carries its display choices, which ship with the Plugin: optional help text, whether it appears in the right-click menu of an area, a place, or a point, and whether its listed places show on the map by default. The menu and the map are off unless the Plugin turns them on. A Plugin should be really easy to configure: an admin only adds or removes it. The Command Interface builds each action's form, menu entry, and result view from the description. A new kind of common piece is a Protocol change the owner decides.

An answer is made of the same three things for every action, in any mix:

  • Places. Points, lines, or areas the Plugin lists and returns to the caller, such as "Main St Hospital" at a position. They are not stored as geo features, and show only on the asking operator's map until that operator saves one as a place. Listed imagery is not allowed: an image a Plugin wants on the map is an imagery geo feature the Plugin creates.
  • Short facts. A label and a value, such as "Wind: 12 m/s from the west".
  • References. The Plugin creates geo features (including imagery) or Objects in Core, and the answer names them. They enter the shared picture and stay in Core until the next Reset, where every operator sees them. Plugins create nothing else: Observations come only from Assets.

An empty answer means the Plugin found nothing. A list never holds more than 1000 items. A Plugin that would need more fails with a clear message, such as "Area too large, pick a smaller area", so a partial list is never mistaken for the whole answer.

What the operator sees

  • Only Plugins that are running can be used. If a Plugin is not connected, Atlas says so at once. Nothing waits and runs later.
  • A call ends with a result or a failure. If a Plugin fails or disconnects partway, whatever it already stored stays, and the call is marked not finished. Nothing reruns by itself; the operator calls again if they still want it.
  • There is no stop. An operator who no longer wants an answer ignores it.
  • Everyone can read every call and answer. Every logged-in operator sees every Plugin call and can read its answer, because Atlas keeps one history. Listed places show only on the asking operator's map until that operator saves one as a place; geo features the Plugin creates appear on everyone's map.
  • Calls are not repeated. The operator runs a call again when they want new data.

Objects

An Object is a file Core holds, such as a photo or a satellite image. Plugins, operators, and Assets add them. An operator can attach a photo to a building's geo feature, for example.

  • A file never changes. An operator can move an Object to another geo feature or detach it, and can delete it. A deleted Object is hidden from operators until the next Reset but not destroyed: the Reset ZIP keeps it, marked deleted. History keeps the record that it was stored and who deleted it.
  • An Object belongs to at most one geo feature. Deleting the geo feature leaves its Objects.
  • A file may be at most 100 MB by default; an admin may change the limit with the max_object_bytes setting.
  • An Asset's file, such as a drone photo, shows on the map only through a geo feature the Asset creates alongside it (Objects).
  • A GeoTIFF, an image that carries its own map position, can be shown on the map as an imagery geo feature, added by operators and Plugins (imagery rules).

Examples

These show how Plugins could be used. No specific Plugin or action is part of the first build.

Find the buildings in an area

The operator passes a box and asks for every building in it. The Plugin asks the Overpass API for OpenStreetMap structures in that box and returns them as a list.

Analyze a building

The operator picks a building and asks the Plugin to analyze it. The Plugin runs whatever open-source tools it has. It creates a geo feature on the building. Its findings never go on the geo feature. Depending on the action, they come back as a list or as Objects attached to the geo feature. The output is a reference to that geo feature.

Gather imagery for an intelligence package

The operator passes an area and asks for satellite imagery of it. The Plugin collects GeoTIFF imagery through its tools, stores each file as an Object, and adds an imagery geo feature for each, so the images show on the map where they belong. The output refers to what it stored.

Terrain and ground elevation

A terrain Plugin for Core and Assets is in the drawer.

More Plugins that fit

  • Points of interest. Takes a box and a kind, such as hospitals, helipads or open fields, and returns named positions found through Overpass.
  • Airspace. Takes a box and returns airspace shapes with their altitude limits, from open airspace data.
  • Weather. Takes a position and a time, and returns wind, visibility and cloud base from an open weather service.
  • What is this place. Takes a position and returns its place name or address.
  • Line of sight. Takes a position and a height, and creates a geo feature showing what can be seen from there.

Not Plugins

  • A live aircraft or ship feed. It runs all the time, so it is an Asset.
  • A geofence alarm. Nobody calls it; it reacts when an Asset or Observation enters an area.
  • An auto-patrol that sends Tasks to drones. It directs Assets.
  • A suggested flight path. A Plugin does not return a route or positions meant to be turned into Tasks.
  • Repeating a call, such as weather every 10 minutes. The operator calls again when they want new data.
  • Turning on Asset lights at dusk. It changes Asset settings.
  • A radio bridge. That is a gateway and its Fieldlink.
  • The Reset archive. That is Core's own job.
  • Map styling. That belongs to the Command Interface.

Not decided

Plugins and Objects in the interface shows how operators run Plugins and see their results and Objects. A new Plugin needs no change to the Command Interface.

Whether a Plugin writes its own Reset ZIP is not decided; for now, Core's ZIP records every call and answer.
