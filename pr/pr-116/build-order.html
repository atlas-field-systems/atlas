Build order after the first version

The owner decided this order on 2026-11-14 (decision log). The numbered steps are the working plan for carrying it out.

Protocol, Core, and the SDK, with their simulations, form the built first version. This page orders the parts that follow.

Design the whole product, then build it

Atlas is designed as the complete product before the real build. That covers Assets, Tasks, settings, reports, history, accounts, geo features, Objects, Observations, Tracks, Fusion, and Plugins. Throwaway prototypes test the design first.

The build then goes one part at a time, in order, and each part is built whole (ADR-0003). The first version was Protocol, then Core, then the SDK, with the Simulations that test them together. Building one part finds problems that change how the next is built, so each part starts from what the last one taught. Core's pillars, for example, were built together, not Entities first, then Tasks, then Objects, because they share much of their underlying code.

The target is the full simulation

The goal says how Atlas is shown to work: a simulation of a whole operation that runs the real code of every part, with no real hardware. The Asset app now runs over IP; the gateway app and Fieldlinks are still unbuilt. The build order aims to make the full simulation runnable as soon as possible.

Decided: the parts the full simulation needs come first

After the first version, the Asset app, the gateway app, and the Fieldlinks are built before the Command Interface. The order among those three is the working plan below, not an owner decision.

The cost is that nobody can use Atlas by hand until the Command Interface is built. Until then the owner judges Atlas from simulation results.

Two risks the order must answer

  1. Do Atlas Tasks and failsafes fit a real autopilot? The initial Asset runtime now runs against ArduPilot SITL. The Asset simulations document the verified scenarios and remaining conformance target. Hardware behavior remains unverified.
  2. How much does the radio really carry? The Meshtastic bench work addresses the unknown radio capacity.

The Meshtastic Fieldlink comes first

Meshtastic is the first Fieldlink. It is closer to the Fieldlinks Atlas will see later, so the gateway app and the simulated radio link are shaped by it. SiK is not a Fieldlink: first flight uses the SiK tool, which runs the Asset app over IP and needs no gateway (ADR-0018).

The Meshtastic folder owns its sketch and bench plan.

New failsafe and radio decisions wait

No new failsafe or radio decision is made until the Asset app has run against simulated ArduPilot and the radio is measured. Decisions already made stay in force. After the results, they are reviewed against what was found.

The steps

  1. The Asset app, built whole, with no throwaway prototype first. The IP runtime and initial ArduPilot SITL scenarios are built; implementation gaps remain. Simulations now use the real app for IP Asset work.
  2. The gateway app and the Meshtastic Fieldlink, over a simulated radio link. Meshtastic stays documentation only for now; see its sketch and potential concepts.
  3. The SiK tool, the Asset app and its MAVLink adapter on a ground Pi. Planned.
  4. Simulation tools and the full simulation. The existing harness runs Core, SDK, and Asset IP scenarios. Radio simulation and tools for writing the full operation remain planned. That operation has Assets take off and make Observations, other Assets tasked onto them, Fusion making Tracks, a radio link failing, and hardware faults.
  5. The Command Interface. Planned; no application code yet.
  6. First flight in the field (First flight). Planned.

Each part is still built whole, as above.
