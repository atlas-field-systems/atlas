The Atlas charter

Atlas helps operators understand field systems, request work, and retain evidence. Read the operating environment before designing a subsystem.

Everything is a draft

Atlas is greenfield. It is deployed nowhere and has no users to stay compatible with. Every part of this repository, this Charter included, is a draft: any decision, law, message, plan or piece of code may be reworked, rewritten or removed, and new ideas are welcome. Nothing is locked. When something has a problem, consider reworking it from the ground up before patching it.

Draft does not mean quiet change. Propose the change and its reason; the owner decides.

Keep Atlas understandable

The owner must be able to read the docs whenever they change. Use short user stories and visible data flows to expose mismatches with intended use. Describe and review the intended user-visible flow before implementing it. Keep unresolved product decisions visible in the owning subsystem's documentation. Put a consequential restriction in its owning system's story before adopting it.

Keep the systems replaceable

Atlas is a walled city. Core and Fusion sit inside the inner wall. Plugins sit in the second ring and reach Core only through its Plugin interface. Gateways, Assets, and operator applications sit outside the city and reach Core only through the public Core API. Design decisions has the layout.

Inside Core, Entities, Tasks, and Objects keep interfaces small enough to rebuild one without rebuilding Atlas. Authentication and administration support them.

Core retains the shared picture and requests for work. Separate projects provide vehicle control, field links, map rendering, and operator applications. The system overview shows how those parts fit together.

Keep evidence honest

An accepted request and an observed result are different facts. Receiving a report does not prove fresh measurements or two-way contact. Each subsystem defines how it represents that evidence.

Keep shared data simple

The owner decides Atlas's data formats and data structures. Protocol follows them and adds the exact fields.

  • Shared domain data lives in Protocol as records, such as Tasks, settings, and reports. Core, clients, gateways, and Assets use the same variables, names, units, and shapes. Local process configuration and diagnostic logs belong to the component that uses them; they are not Protocol contracts.
  • Each record has one time for the whole record. Mixed times are rare and need their own case. Records about one Asset carry asset_id. Where it matters, a record has a field for who requested or reported it.
  • Times are in milliseconds. Only specialized radio data uses nanosecond timing.
  • Counters are ordinary numbers, not long numbers written as text.
  • IDs that people read or that cross a field link are 1 to 4 letters or digits. Admins choose asset_id; Core assigns the others. Event IDs are integers.

Document ownership

  • This charter owns Atlas's purpose, operating context, project-wide principles, and end-to-end usage examples.
  • Subsystem documentation owns its behavior, failure cases, and planning decisions.
  • Protocol owns the exact shared records and their validator within the charter's shared data rules. Core owns the Core API and server mechanisms. The SDK owns the client for that API. Gateway documentation, once written, owns gateways and their Fieldlinks. Asset owns how an Asset behaves, and Command Interface owns how the operator application works. Other components own their runtime details.

Keep each rule with its owner and link to it from other documents. When a subsystem rule conflicts with the operating context, surface the mismatch and resolve it explicitly. Neither document silently overrides the other. Intended behavior is not proof of implementation.

Keep judgment sharp

Coding agents uphold these fundamentals before changing Atlas. Subsystem AGENTS.md files point here. Architecture detail lives in design-decisions.md.

Fix the real hole. Adding a new concept, field, or mechanism to paper over a bug is a design problem. Prefer deleting the wrong thing over layering a new one.

Name important domain distinctions early so first flight does not conflate them (for example Observation versus Track). Keep untested shapes provisional until a concrete story, consumer, or prototype establishes what the contract needs. Commit an exact contract early only when postponing creates a specific, explainable obstacle. Do not let an imagined future architecture indefinitely delay first flight; do not let first-flight shortcuts define the whole architecture either.

Protocol's published package version is its only version. Definitions and records carry no protocol version. Package dependencies select the definitions a program uses. The Core API and each Fieldlink report the hash of the definitions they use, and a mismatch is refused with an explanation. Never silently reinterpret unsupported records or conceal incompatible behavior. Do not invent record fields for attribution or routing that Core or a gateway already owns.

Protocol is the spec and owns the one validator. Core implements the Core API and keeps the business rules. The SDK is the client for that API, and gateways run Fieldlinks. No program builds a second validator. See design-decisions.md.

How-it-works docs, laws, and the Core API doc beat an implementation plan when they conflict. Change them on purpose with the owner; do not quietly diverge in code.

Accepted acknowledgment and observed Asset outcomes are different facts. Asset reports are the observed outcome under the contract, not the same fact as acceptance. Preserve uncertainty when the outcome is not known — see Keep evidence honest. State guarantees together with their assumptions and recovery boundaries. Make retries safe so a repeated request never repeats an effect. Exact rules belong in the Core API and Fieldlink docs.

The SDK, gateways, and Fieldlinks carry requests, reports, and contact. The Asset app owns motion and failsafes. No other component controls flight.

Core, gateways, Assets, and the libraries they use provide detailed diagnostic logging from the start. Each program collects its own events and its libraries' events for its run archive. Their owning docs define logging and configurable options; Protocol defines shared data, not a runtime logging service.

Stress undecided ideas with small prototypes and write findings back into the docs. The docs stay the source.

Every coding agent reads and upholds this charter and design-decisions.md. The Charter is the review standard. Reading or quoting it does not prove a change meets it. A change should make clear what problem it solves, why this is the simplest credible fix, and what evidence supports the claim.

Change Atlas deliberately

The owner approves behavior and scope. Engineers choose conforming details. Keep selected decisions, proposals, and open questions distinct in subsystem docs. Coding agents and their subagents follow this charter and design-decisions.md. When evidence shows an approved assumption is wrong, the agent explains the mismatch and proposes the smallest correction; the owner still decides. Generated output, reviews, and historical specifications do not approve changes and do not override this charter.
