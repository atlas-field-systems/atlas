Runs and identity

What a run is, what Reset does, what carries over, and how Assets get and keep their IDs. This page owns those rules. The Core API has the calls behind them, Core Reset the ZIP, and Gateway what every Fieldlink provides. The decision log dates each decision.

A run and Reset

  • A run lasts from one start of Core to the next deliberate stop.
  • Stopping Core is Reset. There is no Reset request, API call, or button. The admin stops Core on its own computer. The operator is trusted to shut the Assets down first; Core does not check. An Asset left running into the next run is not supported.
  • No retention. Core writes its Reset ZIP, checks it, and only then deletes the run's data. The ZIP is then the only copy of the run, and nothing deletes a ZIP automatically. If the ZIP fails, Core deletes nothing and tries again at its next start, but never serves that run through the Core API.
  • A crash resumes the run. If Core crashes, loses power, or its computer reboots without a deliberate stop, its next start continues the same run: the same run_id, the same Asset IDs, and the same Task numbering. Nothing is reset. Assets, gateways, Plugins, and operators reconnect as after a dropped link. A crash while Core was already stopping finishes that stop at the next start (Core Reset).
  • Everyone signs in again after Reset. Every session ends with the run; a crash ends none.
  • Operator state is discarded. Shared links, hidden Tracks and other view filters, drafts, and result overlays belong to one run. A link names its run, and a link from an ended run never opens an item of the new run.
  • Each part writes its own ZIP: Core, each Asset, and each gateway. Merging them is a separate process.

Scope: only a deliberate stop of Core ends a run. Within a run nothing in the picture expires, and neither a dropped link nor a crash of Core ends anything.

IDs

  • Core assigns every asset_id when the Asset registers, every run, and the acknowledgement tells the registrant: the Asset on IP, or the gateway for a radio Asset. Nothing picks its own asset_id, and no configuration holds one.
  • Assets choose observation_id, unique for that Asset within a run.
  • Core assigns the other IDs: task_id, track_id, geofeature_id, and object_id. They start again each run, so the same ID can name a different item in the next run.

Scope: an ID holds for one run. Within the run an Asset keeps its asset_id through reconnects, app restarts on the ground, and Core crashes; in the next run it gets a new one.

Keys and registration

  • Admins hand out keys, not IDs. An admin creates a key for each Asset on IP, gateway, and Plugin and copies it into that program's configuration. An Asset key names no Asset. There is no enrollment key.
  • An Asset on IP registers itself with its key when it starts. Each key registers at most one Asset at a time. Registering again with the same key in the same run returns the same asset_id, unless an admin removed that Asset; then it registers as a new Asset with a new ID.
  • A restarted app rejoins as itself. Nothing restarts the app on its own. If an Asset's app is started again on the ground during a run, it registers with its key and comes back as the same Asset, with the same asset_id. This holds even if it forgot its ID: the key proves which Asset it is. It still never picks or configures its own ID.
  • Work does not resume after a restart. A restarted app drops its queued Tasks: operators see them marked not done and send again whatever still matters. Nothing resumes on its own. An app that fails in flight stays down, shown offline, while the flight controller returns the vehicle home (Failsafes).
  • A removed Asset's ID ends. If it registers again, it is a new Asset.

Radio Assets

  • The gateway is an IP bridge. A radio Asset holds no Core key and never calls the Core API. It authenticates to its gateway through its Fieldlink. Radio identity stays on the gateway side; Core knows radio Assets only by asset_id.
  • No advance setup. The gateway registers a radio the first time it hears it in the run. Core assigns its asset_id, and the gateway tells the radio. There is no approval step.
  • A restarted radio rejoins as itself. If a radio Asset's app stops and starts again during a run, it identifies itself to its gateway through its Fieldlink and keeps its asset_id. Its work does not resume, as for any restarted app.
  • A removed radio can come back. If it is heard again, the gateway registers it as a new Asset with a new ID.
  • One gateway for the whole network. One gateway is deployed per area (Scale). The radio network is a mesh: Assets talk to each other and to that one gateway, and every radio Asset in the area rides on it. No Asset uses two gateways. Several gateways in one network, and moving a radio Asset to another gateway while it keeps its ID, are out of scope.

When the gateway changes

  • Removed. Its radio Assets stay in the picture, offline. No other gateway takes them over.
  • Replaced by another gateway mid-run. The new gateway registers each radio it hears as a new Asset with a new ID. The old Assets stay in the picture, offline, and their unfinished Tasks are not carried over.
  • Key replaced. The gateway and its radios are unaffected.

Scope: these hold within a run. In the next run every radio registers again as a new Asset.
