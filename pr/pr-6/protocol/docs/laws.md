# Protocol laws

The rules every Atlas message follows. If a change breaks a law, the change is wrong,
or the law gets changed on purpose first.

**Bloat is the enemy, but good organization is not bloat.** Every field, record and message must earn its place, and nothing is defined twice. For example, listing the same command kinds under two message types is bloat. Grouping messages into folders is not.

"Checked" means `npm run check` fails when the law is broken.

1. **Protocol defines shared domain data.** It defines messages and domain-storage records. Core, the SDK cache, and Assets use the same variables, names, units, and shapes. Extra domain-record fields, such as when a message was received, are defined here too. Local configuration and diagnostic logs belong to their runtime components and are not Protocol formats. Core's tables are in [Storage](storage.md); stored record formats are not defined yet.
2. **Flat messages with a creator.** Every field sits directly in the message. No header or wrapper. Every message carries `from`: the creator's ID (an Asset's `asset_id`, an operator's `operator_id`, or `CORE`). Message types are grouped only by the `type` name, never by a wrapper object. A component groups fields that belong together, such as a `position` or an Asset's `settings`. *Checked.*
3. **Every message starts the same way:** `type`, `time` (milliseconds since 1970, UTC), `seq` (the creator's own counter), `from`, then `asset_id` if its type concerns a single Asset, then `kind` if its type has kinds. `asset_id` is required on every message that concerns a single Asset; a message about many Assets (such as asking Core for all of them) leaves it out. *Checked: the first four are required everywhere, and `asset_id` always comes from its variable.*
4. **Variables are the building blocks.** Each field is defined once, in `variables/`, and reused everywhere. Messages, kinds and components only point at variables or components. *Checked.*
5. **No redundancy.** Never send the same fact twice in one message, and never send what the other end can work out on its own.
6. **Full readable names, always.** Field names are whole words, such as `altitude_reference`, and `type` is the full group and type name. The protocol defines no short keys and no type numbers. Each link chooses its own compression (law 12).
7. **Messages are grouped like folders.** A message's `type` is its group and type joined by a dot, matching its file `messages/<group>/<type>.json` (for example `control.command`). A type with several kinds requires `kind`, and each kind is its own file `messages/<group>/<type>/<kind>.json` whose name is the `kind` value. Kinds are unique within a type. *Checked.*
8. **Fixed units.** Metres, metres per second, degrees from true north. Every altitude says what it is measured from. Every uncertainty is a 95% bound: the true value is inside it 95 times out of 100.
9. **Settings are end states.** A setting says what it should be (`lights: on`), never "toggle" or "switch".
10. **Package release identity only.** Protocol's published package version is its only version. Definitions, examples, and messages contain no protocol version, and links do not negotiate one. Programs select definitions through their package dependency. Deployments test their selected package combination; hello acceptance proves authentication, not schema compatibility. Published packages never change, and no backward-compatibility layer is required.
11. **Tools only display.** The CLI and the viewer read everything from `definitions/`, never name a message, and never send anything. *Checked by tests.*
12. **No size cap or chunking in the protocol.** Atlas runs over many links. Each link handles its own size limits, splitting, and compression. The opening hello (`admin.hello`, `admin.operator_hello`) and Core's `admin.hello_reply` are never compressed; the link profile defines how subsequent traffic is encoded.
13. **Easy to compress and split.** Keep structure predictable and fields small: text and lists have length limits, and there are no giant single fields such as embedded files. *Limits checked.*
14. **Asset data reports are fixed.** Every Asset reports the same data the same way, using defined reports and components. No free-form or misc fields. New kinds of data get a new defined report.
15. **One command kind per action.** Each action is its own command kind even when its fields match another (a payload drop and `move_to` both take a position), because meaning and success differ and `admin.describe` declares support per kind. Shared fields reuse the same definitions instead of copies. Plugin actions follow the same rule: each action is one kind of `plugin.call` and `plugin.result`, and `plugin.describe` declares which actions a Plugin offers.
16. **Assets observe; fusion decides tracks.** Assets send observations, never tracks. Tracks come only out of the fusion module.
17. **Keys only in the opening hello.** Asset and operator keys (and the enrollment key) travel only in the hello that opens a link, never in any other message. Core stores only their hashes and never sends a key. An Asset's reports, commands and cameras travel in a separate keyless `admin.describe`, which Core stores and forwards unchanged. Keys are short (16 bytes).
18. **The Asset carries its whole task list.** Each Task's body is sent once. A `control.queue` gives the order as `task_id`s; it takes effect only once every body in it is on board, and is ignored when built on an old `queue_version`. An Asset never runs a `task_id` twice, and a Task's state only moves forward.
19. **Every failure has a defined safe response.** Any failure on the Asset triggers its configured failsafe. Each trigger has a response setting, and it overrides paused. Low battery can never be set to continue. An Asset never stays airborne until it falls.
20. **Routing belongs to links.** No message carries a route, hop or gateway field. A message seen twice (same `from`, `seq` and `time`) is handled once; a retry is that same message, unchanged. Every other message a creator sends gets a new `seq`. Core forwards other creators' messages unchanged (same `from`, `seq` and `time`). A deliberate repeat of content is a new message with a new `seq` from its creator.
21. **Core answers every operator message.** One `admin.reply`, accepted or refused with a reason. For a `plugin.call` it may also be failed with a reason: the Plugin ran and broke. `reply_from` and `reply_to` name the operator message's (`from`, `seq`). Only the Asset's reports confirm an effect. For a query or a `plugin.call` the reply comes after the answer and marks its end.
22. **One link per ID.** Each Asset and each operator interface has its own ID. If a second link opens with the same ID, the newer link replaces the older.
23. **What must arrive is acknowledged.** Core acknowledges an Asset's `admin.describe`, its connect `report.settings` and each final task report with `admin.reply`, and the Asset resends each unchanged until it is. After an accepted hello the Asset sends nothing else until Core has acknowledged its describe and then its connect report, and Core passes nothing on to it until it has acknowledged that connect report. Core's messages to an Asset are acknowledged by the Asset's reports (its queue report for a task list, `report.settings` for a settings change or cancel), and every operator message by `admin.reply` (law 21).
