Using Atlas

This page describes the intended operation. See the repository overview for what is built and what remains planned.

An operator uses the Command Interface to watch Assets and request work. Core keeps the shared picture, the requests, and the event log. A gateway carries Atlas across a field link. The Asset app controls its equipment and reports what happened.

The city is laid out in rings (ADR-0020):

  • Inside the inner wall. Core runs in one process, built from pillars over shared storage and the event log.
  • The second ring. Each Plugin is its own program. It connects out to Core with its own key and reaches Core only through the Plugin interface, never its storage. Core never calls a Plugin and never runs one in its own process. The Plugin interface is the Core API calls a Plugin's key may use, not a second protocol.
  • Outside the city. Gateways, Assets, and operator applications reach Core only through the public Core API.

Most physical Assets use the gateway path, through the gateway's one Fieldlink. A direct-IP Asset calls the Core API itself. A Core may run several gateways, each on its own radio network (Scale), and the gateway design can change as connectivity evolves. The diagram shows responsibilities, not a required network topology.

The first-flight setup is a direct-IP Asset. A ground Raspberry Pi runs the Asset app for the ArduPilot vehicle, through the SiK tool, and talks to the vehicle over a SiK radio. The app represents the vehicle even though it is not aboard it.

An operation runs without planned restarts

Core starts before any other part of an operation and stops after all of them. Each start of Core after a stop begins an empty picture, and stopping Core is the Reset (Reset and identity). Nobody restarts Core during an operation. If it crashes, it keeps the same picture when it starts again, and everyone reconnects. Gateways and Assets stay running too. Links can drop and reconnect while those processes keep their state, and a refreshed Command Interface recovers from Core's event log.

An Asset whose app stops shows offline in Core, and the other Assets keep working. Nothing restarts the app on its own. If it fails in flight, the flight controller returns the vehicle home without Atlas, and the vehicle is inspected before its next flight. An app started again on the ground before the next Reset rejoins as the same Asset with the same ID, because its key proves which Asset it is, but its work does not resume (Reset and identity). An Asset keeps nothing from before a Reset. A dropped link is not a stop: the app keeps its state and reconnects as the same Asset.

An Asset's settings are its current configuration, kept in its entry.

Information-focused stories

These stories describe intended use.

Locate the tracker

A reporting-only Asset is a Raspberry Pi with a GPS peripheral and an uplink. It obtains its own position and reports telemetry to Core for the operator. It accepts no equipment-control commands. If it loses its GPS fix, Atlas retains its last known position and the reported GPS condition. The tracker does not send the old position as a new fix.

Observe an aircraft

An ADS-B receiver is an Asset. It reports Observations about a passing aircraft. Core keeps those Observations in the shared picture for the operator to watch. The operator does not need to control that aircraft to observe it through Atlas.

Research a place

An operator selects a building or area and runs a Plugin action on it. The Plugin returns a list, or creates geo features and stores files as Objects. Every operator sees the call and its result. Plugins has the examples.

Attach a photo to a place

An operator uploads a photo and attaches it to a building's geo feature. Every operator can open it from that place. If it was the wrong building, the operator moves it; if it was the wrong photo, the operator deletes it, and history keeps the record of both.
